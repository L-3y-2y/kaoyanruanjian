## 1. 突出点清单（可直接抄进简历 / 申报书）

### A. 算法与业务建模（最硬的部分）

1. **五轮渐进式记忆状态机 + 两级掌握判定**
   R1 认词 → R2 听写 → R3 默写 → R4 英译中自评 → R5 中译英默写；每词每轮在数据库里是独立记录（5 轮 × N 词一次落库），`memorized_at` 与 `mastered_at` 两个时间戳分别记录"初步记住"和"真正学完"，两级状态可分别查询，不靠前端游标推进。
   *证据：`backend/main.py:226-263,379-390`*

2. **基于 ECDICT `exchange` 字段的词形还原与释义快照闭环**
   从词典变形字段解析 `s:/d:/p:/3:` 等标记，叠加规则兜底，构建 `surface → 原形` 映射（最长词优先 + `setdefault` 消歧），让复数、过去式、句首大写、短语动词在短文里仍可点；点击显示的是**生成当时**的释义快照，词库以后改动不影响老文章。
   *证据：`backend/content.py:66-100,103-135,267-291,380-405`*

3. **生成结果的覆盖率校验与自动修复**
   短文生成后用"与点词标注完全同一套词形映射"反查目标词覆盖率；漏词就带着缺失清单重写一次，仍不达标才降级到本地确定性生成器（保证 100% 覆盖）。避免了"号称包含目标词、实际漏了一半"的假生成。
   *证据：`backend/content.py:223-251`*

4. **可选间隔复习（艾宾浩斯思路的工程化）**
   1/2/4/7/15/30 天排期，答错缩短间隔；开关默认关闭，不改变原有日期批次语义。这一条体现的是"在既有约束下做增量设计"，而不是推翻重来。
   *证据：`backend/main.py:130-160`，`SMART_REVIEW` 开关*

### B. 工程与架构

5. **前后端分离 + 同源单端口交付**：Vue 3 + Vite 开发期代理到 FastAPI `:8000`，构建产物由后端同源托管，最终用户只需双击 `start.bat`，无需配环境。
6. **参数化 SQL 贯穿全项目**：所有业务查询用 `%s` 占位；少数 f-string 拼接处插值来源是代码内白名单（迁移列定义、admin 表名），week_key 额外做 `\d{4}-W\d{2}` 格式校验。SQL 注入面基本为零。*证据：`backend/db.py:60-73,110-140`，`main.py:635-636,688-694`*
7. **服务端身份解析，不信前端传参**：Session-Cookie（`secrets.token_hex(32)`，HttpOnly / SameSite=Lax / 30 天），身份只从 cookie 解析；所有业务 SQL 带 `user_id` 过滤，越权与不存在统一返回 404。密码存 pbkdf2-sha256 200k 轮 + 随机盐，用 `hmac.compare_digest` 比对。*证据：`backend/auth.py:32-49,57-87,104-119`*
8. **事务边界清晰 + 幂等增量迁移**：答题的"进度更新 + 日志插入"在同一个事务；启动时查 `information_schema` 后只 `ADD COLUMN` / `MODIFY NULL`，无 drop / truncate，老数据一行不动。*证据：`backend/db.py:45-57,103-140`，`main.py:403-471`*
9. **真·端到端自检 13 项**：`scripts/verify_full.py` 用真实 CookieJar 打 HTTP 接口 + 真实 MySQL，跑完 R1～R5、短文揭示、周阅读判分、防重复提交、多用户隔离，测试数据自动清理；不是 mock 自测。*证据：`scripts/verify_full.py:39-60,97-129,209-275`*

### C. 数据与 AI

10. **4803 词真实词库**：102 个内置高频样本 + 4701 个 ECDICT `ky` 考研词，INSERT IGNORE 保证老 progress 的 word_id 引用不变。
11. **可配置生成层 + 主备切换 + 离线降级**：`generate_text` / `generate_json` 统一入口，base_url/model/key 全从 `.env` 读、不写死模型名；主通道失败自动切兜底；`_extract_json` 容忍代码围栏和前后废话，格式不合法做一次修复重试；主观题判分结果缓存避免重复烧 token；**没配 Key 时全流程仍可离线运行**。*证据：`backend/llm.py:31-43,46-56,78-116,119-148`*
12. **大模型出题而非模板出题**：周阅读 5 道题由模型按正文一次生成（4 道四选一 + 1 道简答及评分要点），并校验选项/答案格式；失败才回退模板。解决了"答案永远是 A、干扰项与文章无关"的假题问题。

### D. 产品与体验

13. **首次渲染纯文本，揭示才标注**：目标词在揭示前与正文其他词外观完全一致，避免提前泄露考点；揭示状态落盘，刷新后保持。
14. **场景化短文 + 前端语境完形**：进入批次前可选校园/实验室/职场/新闻/旅行，场景存 `article.scene` 且已生成文章不重写；揭示后前端用释义快照自动拼最多 5 道完形题，干扰项取自同篇词，纯前端练习不写库。

### P1 — 面试 / 答辩大概率被追问

| # | 问题 | 证据 | 建议改法 |
| --- | --- | --- | --- |
| 4 | **长事务跨网络调用**：一次周阅读生成在 `with transaction()` 里串行跑多次 LLM 调用，`LLM_TIMEOUT=12`，单次可能持锁 30～60 秒。 | `main.py:626-629`、`content.py:230-251,577-598` | 把生成挪出事务：先用无事务连接读词、在内存里生成文章和题目，再开事务只做 INSERT。持锁从几十秒降到毫秒级。 |
| 5 | **并发幂等只有应用层"先查后写"，缺数据库唯一约束**：两个并发请求都可能读到 `pending`，第二个 UPDATE 影响 0 行却仍写日志并返回成功。 | `main.py:419-434`、`mark_done` 返回值被丢弃；`schema.sql:81-96` 的 `answer_log` 无相关唯一键 | 让 `mark_done` 返回 `cur.rowcount`，0 行走 duplicate 分支；给 `answer_log` 补 `(user_id, question_id)` 唯一键兜底。 |
| 6 | **LOCAL_MODE 回环信任 + 管理员直通**：一旦挂同机反向代理或改成 `--host 0.0.0.0`，外部请求会被当成"本机"，直接拿到管理员词库权限。 | `auth.py:52-54,94-99` | 对外部署时强制 `LOCAL_MODE=0`；去掉管理员直通或改为显式开关；拒绝带 `X-Forwarded-*` 的请求。README 写死"单 worker、禁止反代透传为回环"。 |
| 7 | **`GET /api/state` 带副作用**：读状态时做 stage 跃迁和批量 UPDATE，违反幂等语义，可被预取/爬虫触发。 | `main.py:215-263,333-341` | 抽成 `advance_if_complete()`，由 `POST /api/answer` 成功后调用，`/api/state` 保持纯读。 |
| 8 | **登录无限速**：PBKDF2 200k 轮只提高单次成本，挡不住在线爆破。 | `auth.py:187-196` | 加 5 次/分钟的失败计数与锁定（一张表或进程内字典即可）。 |

### P2 — 有时间再补（体现工程成熟度）

- 全后端没有 `logging`，定时任务异常被 `except: pass` 静默吞掉（`main.py:57-63`、`db.py:53-55`、`content.py:260/607`）——补一个最小日志模块，至少记录周次、user_id、异常类型。
- `/api/auth/users` 无鉴权、会枚举用户名（`auth.py:221-229`）；`/api/health` 回显数据库账号（`main.py:307-320`）——前者加 admin 依赖或删掉，后者去掉 `CURRENT_USER()`。
- 周阅读"本周词"回退查询脱离周次，会拿任意历史已掌握词（`content.py:437-453`）——加回 `study_date BETWEEN 周一 AND 周日`。
- 词形规则兜底会生成 `prefered` / `runing` 这类错误变形（`content.py:78-88`）——补双写辅音和 `y→ies` 映射表。
- `requirements.txt:5` 声明了 `bcrypt` 但代码全用 pbkdf2——删掉未使用依赖。
- R1「陌生」和 R4「揭示」重复提交会累加 `wrong_count`，可人为刷高抽词权重（`main.py:425-431,453-456`）——加幂等。

## 3. 三个场景分别怎么用这份材料

### 3.1 写简历（STAR 示例，可直接改）

> **考研词汇自适应学习系统**（个人项目 · 2026.03–2026.11）
> - 独立设计五轮记忆状态机与两级掌握模型，基于 FastAPI + MySQL 实现每词每轮独立进度追踪，进度更新与答题日志同事务持久化；
> - 基于 ECDICT 4701 个考研词构建 4803 词词库，实现 `exchange` 词形还原映射与释义快照机制，使短文中的变形词可被正确标注；
> - 设计可配置的大模型生成层（主备切换 / JSON 修复重试 / 离线降级），实现场景化短文与按正文生成的阅读理解题，并用同一套词形映射做覆盖率校验与自动补词；
> - 编写 13 项端到端自检脚本，覆盖注册隔离、五轮流程、幂等与多用户数据隔离，测试数据自动清理。
>
> **量化补充建议**（写之前去数据库/日志里实测后填进去）：累计学习词数、连续使用天数、短文生成篇数、自检通过率、词库规模 4803。

### 3.2 投比赛

**适合的赛事**：计算机设计大赛、挑战杯、互联网+（职教/创新赛道）、大学生创新创业训练计划。
**不适合的赛事**：纯算法竞赛、要求硬核模型创新的 AI 竞赛——这个项目赢在完整度和实用价值，不赢在算法新颖度。

**包装建议**：
- 项目名从"考研背单词软件"改成**"AI 驱动的考研词汇自适应学习系统"**，突出"自适应"和"AI"。
- 创新点讲三条就够：① 五轮状态机驱动的渐进式记忆（不是简单卡片闪卡）；② 词形还原闭环让生成内容 100% 可点、可追溯；③ 大模型生成 + 覆盖率校验 + 离线降级，兼顾质量与可用性。
- 必须补的"证明"：30 份用户问卷或使用反馈、一次前后测（使用 N 天后词汇测试正确率变化）、至少 3 张真实界面截图 + 1 段 2 分钟演示视频。评审看的是"有人用、有效果"，不是"功能多"。
- 把 README 里"已知边界"那一节如实保留并放进附录——坦诚说明局限反而加分，比吹"全自動智能"安全。

### 3.3 考研复试

**30 秒概述话术**：
> "我自己备考时发现市面上的背单词软件都是固定词表加闪卡，不符合我想要的'五轮渐进 + 语境复用'的学习方式，就自己写了一套。后端用 FastAPI 加 MySQL，前端 Vue 3。核心是把'认词—听写—默写—互译'做成状态机，每轮进度存服务端；再在学完的批次上用大模型生成场景化短文和阅读题，短文里的目标词通过词典变形字段做还原标注，点开能看到生成当时的释义。全程免费模型兜底，没配 Key 也能离线跑。"

**导师可能追问的问题（务必准备）**：
1. 五轮状态机为什么这样设计？和间隔重复（Anki）有什么区别？——答：五轮是**题型递进**（认知→拼写→互译），间隔重复是**时间调度**，两者正交；本项目的间隔复习做成可开关的增量层，默认关以尊重"不做到期提醒"的原需求。
2. 词形还原为什么不用现成 NLP 库？——答：ECDICT 的 `exchange` 字段已经给出了该词的实际变形，比规则/模型更准且零依赖；规则只作兜底。最长词优先是为了处理"一个变形对应多个原形"的冲突。
3. 大模型返回不对怎么办？——答：JSON 提取容错 + 一次修复重试 + 覆盖率校验 + 本地确定性生成器兜底，四级降级，保证功能永远可用。
4. 为什么要 Session-Cookie 而不是 JWT？——答：单机自用、无需跨域、HttpOnly 阻断 XSS 窃取、服务端可随时吊销；JWT 在这个场景没有收益反而增加撤销复杂度。
5. 4803 词怎么来的、质量怎么保证？——答：ECDICT 官方 77 万词条筛 `ky` 标签得 4701 词，加 102 个内置高频样本；ECDICT 是社区整理非官方大纲，`verified=0` 标记未人工核对，这一点在 README 里如实写了。
6. 遇到最难的问题是什么？——建议讲"生成内容和点词标注必须用同一套词形映射，否则会出现'文章里明明有这个词却点不开'"，这是真踩过的坑，比讲"配置环境"有说服力。
7. **"这个项目是你独立完成的吗？"** —— 如实说：需求设计和架构决策是我主导的，编码阶段用 AI 辅助生成（WorkBuddy），每一行我都审核、测试并改过；然后**立刻展示你能讲清的技术点**（上面 1～6 任选两个）。答辩时最危险的不是"用了 AI"，而是"讲不出自己项目里的设计取舍"。

> 提醒：复试前把 `docs/design-decisions.md` 通读两遍——里面 22 节全是"为什么这样做而不是那样做"，这正是导师想听的东西。

### 5.1 管理员端

| 级别 | 问题 | 证据 | 改法 |
| --- | --- | --- | --- |

### 5.4 一个"看起来是问题但其实没问题"的点

`user` 表和 `admin` 表都有独立的自增 `id`（可能都有 id=1），容易担心会话串号。实际上 `user_session` 用 `is_admin` 字段区分，`resolve_user` 分两次查询分别 JOIN `user` 和 `admin`（`auth.py:63-76`），所以**不会把管理员当成普通用户或反过来**。这里不需要改。
